# M4, the graphics card: research (2026-11-12)

Three helpers researched what the owner's PC (a Windows laptop with an NVIDIA RTX 3060 and an Intel Core i7) can do for converting films, and how a server program keeps a laptop awake. Each claim carries its source and how sure it is: *checked here* (run on the shipped converter's Linux build, which has no graphics card to use but prints every option it has), *documented*, *reported by users*, or *my inference*. Nothing here was run on a graphics card: no machine the app is built or tested on has one. The design draft built on this is `M4-hardware.md`.

## NVIDIA (the RTX 3060's encoder, decoder and filters)

### Findings

- **BUILD. The shipped jellyfin-ffmpeg 8.1.3-2 is compiled against nv-codec-headers 12.0.16 (NVIDIA Video Codec SDK 12.0). So the driver it needs is 522.25 or newer on Windows (520.56.06 on Linux). An RTX 3060 laptop first shipped with 46x drivers in 2021, so a never-updated laptop fails. Words printed: 'Driver does not support the required nvenc API version. Required: 12.0 Found: <a>.<b>' then 'The minimum required Nvidia driver for nvenc is 522.25 or newer'. Permanent until the driver version changes.**
  - Source: Ran: strings -n 4 pinned-ffmpeg/ffmpeg | grep -E '^(570\.0|551\.76|531\.61|522\.25|520\.56\.06|...)' -> only '520.56.06' (the Linux string for SDK 12.0), next to 'libnvidia-encode.so.1'. https://github.com/jellyfin/jellyfin-ffmpeg/blob/v8.1.3-2/builder/scripts.d/50-ffnvcodec.sh pins nv-codec-headers 451da99614412a7f9526ef301a5ee0c7a6f9ad76, whose README says 'Video Codec SDK version 12.0.16 ... Windows: 522.25 or newer'. Message text: https://github.com/FFmpeg/FFmpeg/blob/release/8.1/libavcodec/nvenc.c lines 264-339 and 376-383. Jellyfin docs (nvidia.md): 'In Jellyfin 10.11 the minimum required NVIDIA driver version is 522.25'.
  - How sure: checked here
- **BUILD. h264_nvenc in this build has: -preset p1..p7 (default p4), -tune hq|ll|ull|lossless (default hq), -profile baseline|main|high|high444p (default MAIN, not high), -level (default auto), -rc constqp|vbr|cbr, -cq, -qp, -qmin/-qmax, -rc-lookahead (default 0), -no-scenecut, -forced-idr (default false), -b_adapt, -strict_gop, -spatial-aq, -temporal-aq, -zerolatency, -delay, -surfaces, -multipass, -b_ref_mode, -dpb_size, -a53cc (default true), -gpu (default any; 'list'). It does NOT have the newer SDK options (tf_level, lookahead_level, unidir_b). Defaults: b=2M, g=-1 and bf=-1 (preset decides).**
  - Source: Ran: pinned-ffmpeg/ffmpeg -hide_banner -h encoder=h264_nvenc (saved as <scratch>/hw.IYnBOa/h264_nvenc.txt). Defaults table: https://github.com/FFmpeg/FFmpeg/blob/release/8.1/libavcodec/nvenc_h264.c lines 256-267.
  - How sure: checked here
- **BUILD. Every option in the recommended encoder line is spelled as this build expects: the run reaches the driver ('Cannot load libcuda.so.1') instead of stopping at option parsing, while a misspelt one stops with 'Unrecognized option'.**
  - Source: Ran: ffmpeg -f lavfi -i testsrc2=s=320x240:r=24:d=1 -c:v h264_nvenc -preset p4 -tune hq -profile:v high -rc vbr -cq 23 -b:v 0 -maxrate 10000k -bufsize 20000k -bf 0 -g 146 -forced-idr 1 -strict_gop 1 -no-scenecut 1 -rc-lookahead 0 -b_adapt 0 -a53cc 0 -fps_mode vfr -force_key_frames 3,6,9 -f null -  -> '[h264_nvenc @ ...] Cannot load libcuda.so.1'. Same with '-strict_gopp 1' -> "Unrecognized option 'strict_gopp'."
  - How sure: checked here
- **KEY FRAMES. -force_key_frames only marks the frame as picture type I. h264_nvenc turns that into an IDR only with -forced-idr 1; without it the frame is a plain intra frame, and ffmpeg flags only IDR packets as key frames, so the fragment cutter would see no cut. -forced-idr 1 is mandatory. It works the same for frames that live on the card (it is a property of the frame, not of its pixels).**
  - Source: https://github.com/FFmpeg/FFmpeg/blob/release/8.1/fftools/ffmpeg_enc.c line 804 (frame->pict_type = forced_kf_apply) ; https://github.com/FFmpeg/FFmpeg/blob/release/8.1/libavcodec/nvenc.c lines 3179-3181 (FORCEIDR if forced_idr else FORCEINTRA) and 2787-2789 (AV_PKT_FLAG_KEY only for NV_ENC_PIC_TYPE_IDR).
  - How sure: documented
- **KEY FRAMES. The encoder's own key frames come from two places. (1) The GOP counter: -g N sets gopLength and idrPeriod to N. (2) 'Adaptive I-frame insertion at scene cuts', which NVIDIA's header says exists only when look-ahead is on. ffmpeg turns look-ahead on only for -rc-lookahead > 0, and only then passes -no-scenecut and -b_adapt to the driver. BUT presets p6 and p7 may switch look-ahead on by themselves, and in that case ffmpeg does not pass -no-scenecut. So: use p1..p5 with -rc-lookahead 0, or, for p6/p7, give an explicit -rc-lookahead N -no-scenecut 1.**
  - Source: nvenc.c (release/8.1) lines 1199-1213 (lookahead block sets disableIadapt = no_scenecut only inside 'if (ctx->rc_lookahead > 0)'), 1890-1895 ('P6 & P7 presets may enable lookahead for better quality'), 1925-1932, 1332 (idrPeriod = gopLength). nvEncodeAPI.h of the pinned headers, lines 1427-1429: 'disableIadapt ... (only has an effect when lookahead is enabled)'.
  - How sure: documented
- **KEY FRAMES. -strict_gop does not pin key frames; it is a rate-control switch ('minimize GOP-to-GOP rate fluctuations'). Harmless, not a guarantee.**
  - Source: Shipped help text ('-strict_gop Set 1 to minimize GOP-to-GOP rate fluctuations'); nvEncodeAPI.h line 1433.
  - How sure: checked here
- **KEY FRAMES. I could not find out whether a forced IDR restarts NVENC's GOP counter. If it does not, '-g <frames in two chunks + 2>' (the design's value) gives an unasked IDR every G frames counted from the run's first frame, which differs per run and breaks the lattice. Only the owner's card can settle it (probe in 'unknowns').**
  - Source: Searched NVIDIA developer forum and ffmpeg-devel threads on NV_ENC_PIC_FLAG_FORCEIDR; none states the counter behaviour. nvEncodeAPI.h lines 698-702 and 1935 say only that FORCEIDR needs enablePTD=1 and that NVENC_INFINITE_GOPLENGTH stops automatic key frames (ffmpeg's -g cannot express that value).
  - How sure: my inference
- **B-FRAMES AND TIMES. With -bf 0 (frameIntervalP=1) every packet's decode time equals its show time. With B-frames ffmpeg shifts decode times back by a delay it measures from the first frames of that run, so a run's first decode time is negative and depends on where it began: the MP4 header/first fragment then differ between runs. Keep -bf 0 (unset means 'preset decides').**
  - Source: nvenc.c (release/8.1) lines 1933-1936 and nvenc_set_timestamp lines 2625-2665. That the MP4 header differs is my inference from those shifted times, in line with why the design uses -bf 0 for libx264.
  - How sure: documented
- **ENCODER DELAY. With -bf 0 and no look-ahead, ffmpeg's nvenc uses 4 surfaces and holds back at most 3 frames (about 0.125 s at 24 pictures a second), against the 0.7 s the design allows for libx264.**
  - Source: nvenc.c (release/8.1) lines 1048-1083 (nb_surfaces = max(4, frameIntervalP*4); async_depth = nb_surfaces-1) and 2837.
  - How sure: documented
- **JOINABLE OUTPUT. For MP4 output ffmpeg sets the global-header flag, and nvenc then writes SPS/PPS only into the header (disableSPSPPS=1, repeatSPSPPS=0), not into the stream. The SPS is made by the driver from the session's settings (size, profile, level, colour tags, frame rate for the timing fields, reference frames, B-frames); nothing in ffmpeg's code puts per-run data there. So equal arguments should give equal headers; whether they are byte-identical on this driver is a probe. A header from h264_nvenc is never the same as one from libx264: chunks of the two cannot share one header.**
  - Source: nvenc.c (release/8.1) lines 1323-1324, 1296-1345, 1411-1415. Equality across runs: inference, not run.
  - How sure: my inference
- **LEVEL. Jellyfin deliberately gives h264_nvenc no -level: 'level option may cause NVENC to fail. NVENC cannot adjust the given level, just throw an error.' Left at auto the driver picks it from the settings (same every run for the same arguments).**
  - Source: https://github.com/jellyfin/jellyfin/blob/master/MediaBrowser.Controller/MediaEncoding/EncodingHelper.cs lines 2362-2368 (fetched 2026-11-12).
  - How sure: documented
- **RATE CONTROL. '-rc vbr -cq Q -maxrate M' is the constant-quality-with-ceiling mode. When -cq is set, ffmpeg throws away BOTH the average bit rate and the buffer size: 'CQ mode shall discard avg bitrate/vbv buffer size and honor only max bitrate'. So the design's '-bufsize 2M' does nothing with -cq; the driver uses its default buffer. A ceiling with a chosen buffer exists only without -cq (-b:v B -maxrate M -bufsize 2M), which is what Jellyfin uses.**
  - Source: nvenc.c (release/8.1) lines 1255-1266.
  - How sure: documented
- **QUALITY. There is no published, dependable mapping from libx264 -crf to h264_nvenc -cq. Sources agree the scales differ and say to measure. Anecdotes: cq 24-26 tried against crf 21; 'low-to-mid 20s'. Treat the design's cq 24 (or 23) as a starting guess to be measured on the owner's card.**
  - Source: Search results 2026-11-12: dev.to 'Benchmark NVENC vs CPU transcoding' ('NVENC's -cq is not the same scale as x264's -crf ... pick -cq by measuring VMAF'), VideoHelp threads p=2559461, Reddit r/ffmpeg thread on matching crf 21. Pages not opened (hosts not reachable from this session); summaries only.
  - How sure: reported by users
- **SPEED, PUBLISHED. NVIDIA's application notes give H.264 encode speed per encoder engine at 1920x1080 8-bit, measured on an RTX 3090 for the 30-series column: p1 VBR high-quality about 790 pictures a second (SDK 12.2 note) to about 940 (SDK 13.0 note, codec of that row not certain), p5 about 335, p7 about 170. That is 7x to 30x playing speed for 24-picture film even at the slow presets. I found no published 4K figures and none for a laptop 3060 (one encoder engine, lower clocks than a 3090; NVIDIA says speed follows the video clock). Rule of thumb only: 4K is about a quarter of the 1080p rate.**
  - Source: https://docs.nvidia.com/video-technologies/video-codec-sdk/12.2/nvenc-application-note/index.html and .../13.0/nvenc-application-note/index.html, read only through search summaries (docs.nvidia.com is not reachable from this session, so the rows could not be checked cell by cell).
  - How sure: documented
- **JELLYFIN. For the same job Jellyfin passes h264_nvenc: '-preset p1' by default (its 'auto' falls through to p1; veryslow..faster map to p7..p2), no spatial AQ for H.264 ('skipped for now because Maxwell 1 does not support it'), '-b:v B -maxrate B -bufsize 2B' (plain VBR, no -cq), profile high, no -level, and for HLS only '-g:v:0 N -keyint_min:v:0 N' with N = ceil(segment seconds x frame rate).   - Source: EncodingHelper.cs (jellyfin master, fetched 2026-11-12) lines 1817-1838 (preset, AQ), 1654 and 1722 (bitrate), 2040-2090 (key frames), 2362-2368 (level).

- **DECODING, TWO ROUTES. The build has (a) the 'cuda' accelerator on ffmpeg's own decoders (h264, hevc, vp9, av1, mpeg2video, vc1/wmv3, mpeg4, vp8, mjpeg, mpeg1video all list 'Supported hardware devices: cuda') and (b) separate *_cuvid decoders. In (a) ffmpeg's own code still reads the stream, orders the frames and gives them their times; the card only makes the pixels. In (b) NVIDIA's parser does it, and times travel through 100-nanosecond units and back (and are interpolated when it doubles frames). So (a) gives the same frame times as software decoding by construction; (b) is not guaranteed to. Use (a) only.**
  - Source: Ran: ffmpeg -h decoder=h264 (etc.) and -decoders. https://github.com/FFmpeg/FFmpeg/blob/release/8.1/libavcodec/cuviddec.c lines 516-521 and 714-725. ffmpeg-user, Nov 2018: 'nvdec is a proper hwaccel implementation while cuvid is a full decoder implementation using the nvidia parser' (https://ffmpeg.org/pipermail/ffmpeg-user/2018-November/041890.html, via search). That times are identical to software is inference; probe it.
  - How sure: my inference

### Pitfalls

- Without -forced-idr 1 the forced frames are intra frames that ffmpeg does not flag as key frames: no fragments are cut and the lattice check sees nothing at the cut. The option's default is false.
- -bufsize is silently dropped whenever -cq is given (and so is -b:v). The design's hardware row '-cq 24 -maxrate M -bufsize 2M' therefore has a ceiling but no chosen buffer; short bursts above M are governed by the driver's default.
- h264_nvenc's default profile in this build is main, not high, and -bf/-g unset mean 'whatever the preset says'. Give -profile:v high, -bf 0 and -g explicitly.
- p6 and p7 can enable look-ahead by themselves; -no-scenecut and -b_adapt are only passed to the driver when -rc-lookahead is above 0 on the command line. With p6/p7 and '-rc-lookahead 0' scene-cut frames may appear unasked.
- Do not copy Jellyfin's key-frame handling: it gives NVENC only -g/-keyint_min and no -force_key_frames. That is right for its frame-counted segments and wrong for a whole-second lattice at 23.976 or 29.97.
- Giving NVENC a -level that does not fit size, rate and reference frames makes the run fail outright (Jellyfin omits it for that reason).
- '-hwaccel cuda' is not 'use the card if possible' in the way that matters here: with no driver the run fails; with a driver but an undecodable format it logs two error lines and decodes in software, and any *_cuda filter then ends the run with 'Impossible to convert between the formats'. A plan that assumes card frames must know beforehand that they will be card frames.
- '-threads 1' on the input (needed so the card decoder does not ask for too many surfaces) also makes a quiet software fall-back single-threaded: a 4K film would then decode far below playing speed instead of failing visibly.
- The software 'format=' filter (the design's 'chain ending format=nv12') cannot follow card frames. On the card the last pixel-format step is scale_cuda=format=yuv420p or tonemap_cuda=format=yuv420p; 'format=yuv420p' is only valid after hwdownload.
- A 10-bit picture left on the card without conversion makes h264_nvenc fail ('10 bit encode not supported'): every card chain for a 10-bit source must end in an 8-bit format.
- The *_cuvid decoders rebuild frame times through NVIDIA's parser and 100-nanosecond units, deinterlace inside the decoder and carry no Dolby Vision data. For a lattice that needs every run to give every frame the same time, and for Dolby Vision profile 5, they are the wrong route even though they are in the build.
- tonemap_cuda stops at the first frame with 'No DOVI metadata and unsupported input transfer characteristic' when a 10-bit file is not tagged PQ or HLG (untagged HDR files exist). Jellyfin's setparams in front forces the tag; it must then only be used for files the app has judged to be HDR, or SDR 10-bit files would be tone-mapped.
- Phone videos with a rotation tag: ffmpeg would insert a software rotate filter in front of card frames and fail; '-noautorotate' avoids the failure but leaves the picture unrotated. Send rotated files down the software path (or add transpose_cuda later).
- 'OpenEncodeSessionEx failed: out of memory (10)' usually means the session limit, not memory. Marking the encoder as failed on it (the design's 'switched off by its first failure') would switch the card off for good because two people watched at once or a jump overlapped the old run.
- A header made by h264_nvenc never equals one made by libx264, and probably not one made by a different driver version. The probe's 'byte-identical headers from two runs' result should be stored per driver version, and a fall-back to software within a play must restart the stream (as the design's 410 path does).
- The fps filter is fine on card frames, but 'trim' before it and an exact seek remain as wrong as in software; nothing about the card changes decisions 3 to 5 of the design. What the card can change is the picture of the first frames after a jump into a file with unclean key frames: check the lead-in rule by picture, not only by times.
- On a hybrid laptop do not pick the NVIDIA card through a Direct3D adapter number (d3d11va): adapter 0 is usually the Intel chip. CUDA device 0 is the NVIDIA card.
- Published speeds are for desktop RTX 3090 engines at 1080p. Do not put them into the speed table: a laptop 3060 has one encoder engine, lower clocks, heat limits and possibly battery limits. Only measured figures from the owner's PC count.
- The examined binary is the Linux build. The Windows build is expected to have the same NVIDIA encoder, decoders and *_cuda filters, but that is an expectation: Abilities must read them on the owner's PC before any card command is built.

- **[Q1 how a forced key frame reaches the encoder] The ffmpeg program sets pict_type=I on a frame that -force_key_frames selects and pict_type=NONE on every other frame (so key frames of the source never leak through). h264_qsv then asks Intel for an I frame, and adds the IDR bit only if '(frame->flags & AV_FRAME_FLAG_KEY) || q->forced_idr'. Without -forced_idr 1 a forced frame is an IDR only when the source frame happened to be a key frame; otherwise it is a plain I frame. Output packets are marked as key frames only when Intel reports IDR, so a plain I frame would not start a fragment in the cutter. Conclusion: -forced_idr 1 is required, exactly as the design's row has it.**

- **[Q1 key frames nowhere else: GOP counter] ffmpeg maps -g to GopPicSize, -bf+1 to GopRefDist, -idr_interval to IdrInterval (0 = every GOP-start I frame is an IDR). In Intel's open-source runtimes (both the newer VPL runtime for 11th generation and later, and the older Media SDK for 10th and earlier) the type of an unforced frame is computed from its distance to the LAST IDR in display order, and a forced IDR becomes that last IDR. So a forced IDR restarts the count, and with -g longer than a chunk (the design's two chunks + 2) Intel adds no IDR of its own between forced ones, as with x264. ### Recommended

- STEP 0, ask the PC once per program start (about a quarter second, no film needed): ffmpeg -hide_banner -nostdin -loglevel verbose -init_hw_device d3d11va=dx11:,vendor_id=0x8086 -init_hw_device qsv=qs@dx11 -f lavfi -i nullsrc=s=64x64:d=0.1 -frames:v 1 -f null -   WHY: one run says whether an Intel adapter exists ('Using device 8086:XXXX (name).' or 'Failed to find d3d11va adapter by vendor id 0x8086'), whether Intel's media runtime loads, and its version ('Initialize MFX session: implementation version is M.m': 1.x = 10th generation or older, 2.x = 11th or newer). Keep every line in the support bundle. Ask again at each start because the answer can change.
- STEP 1, first Intel path = encoder only; decoding and the whole filter chain stay exactly as in convertArgs, ending format=nv12 instead of format=yuv420p. Global: -init_hw_device d3d11va=dx11:,vendor_id=0x8086 -init_hw_device qsv=qs@dx11   Encoder: -c:v h264_qsv -preset veryfast -profile:v high -b:v <M> -maxrate <M+1> -bufsize <2M> -bf 0 -g <frames in two chunks + 2> -forced_idr 1 -idr_interval 0 -adaptive_i 0 -adaptive_b 0 -look_ahead 0 -fps_mode vfr -force_key_frames <as today>   WHY: the lattice arithmetic is untouched because fps/trim/scale are the same software filters; only the encoder is new. The rate shape (-b:v M -maxrate M+1) is Jellyfin's, the one with the most field use; the key-frame flags are the ones the source shows to be needed. The price is that it spends about M on every scene. For ordinary 1080p films the encoder was the slow part (3.8x at veryfast against 17x decoding), so this step alone should lift them well clear of the bar.
- Alternative rate line to try in the hardware test, not as the default: -global_quality 23 -b:v <0.6 x M> -maxrate <M> -bufsize <2M>  (ffmpeg then selects QVBR, Intel's quality-with-ceiling mode). WHY: closest to the software row's '-crf 22 -maxrate M'. Use only if the test's verbose log shows 'RateControlMethod: QVBR' and no 'Selected ratecontrol mode is unsupported'. The 0.6 and the 23 are starting values of mine with no source. Never write -global_quality with -maxrate but without -b:v.
- STEP 2, SDR film decoded and shrunk on Intel graphics (for sources larger than the target; needs STEP 1 proven first). Global as STEP 1 plus -filter_hw_device qs. Before -i: -hwaccel d3d11va -hwaccel_device dx11 -hwaccel_output_format d3d11 -noautorotate -threads 2  then the usual -ss/-noaccurate_seek/-readrate/-i. Filters: -vf fps=NUM/DEN:start_time=<A>,trim=start=<P>,hwmap=derive_device=qsv,vpp_qsv=w=W:h=H:format=nv12:passthrough=0,setsar=1   Encoder as STEP 1.   WHY: this is Jellyfin's default Windows arrangement (FFmpeg's own decoder with the chip doing the pixels, mapped to QSV, vpp_qsv with passthrough=0), with fps and trim moved to the front so that frame times are fixed before any Intel filter can re-round them. The chain ends on the card: no format=nv12 after it.
- STEP 3, HDR film (4K HEVC 10-bit, the case that needs help most), same colours as the software path: as STEP 2 but -vf fps=NUM/DEN:start_time=<A>,trim=start=<P>,hwmap=derive_device=qsv,vpp_qsv=w=W:h=H:passthrough=0,hwdownload,format=p010le,tonemapx=tonemap=bt2390:desat=0:peak=100:t=bt709:m=bt709:p=bt709:format=nv12  and the design's -color_primaries bt709 -color_trc bt709 -colorspace bt709.   WHY: the 4K decoding (the measured bottleneck) and the shrinking move to the chip; tone mapping stays the one filter already chosen, at the small size, so a chunk from this path looks like a chunk from the processor path and it works on 7th generation and newer alike. Its speed is unknown until the owner's benchmark; if it is short, the next candidate is Jellyfin's tonemap_opencl arrangement, not vpp_qsv tonemap=1.
- Do not use Intel's built-in tone mapping (vpp_qsv tonemap=1) in the first version. WHY: it silently does nothing on 10th generation and older, covers HDR10 only, is reported darker than the bt2390 result, and would make a film change look when a session falls back to another path.
- Keep these kinds of film on the software chain (with the Intel encoder of STEP 1 if it passed): interlaced films (bwdif before fps as today), films with a rotation, 10-bit H.264, anything with burned-in subtitles, AV1 on a PC whose runtime version is 1.x, and Dolby Vision profile 5. WHY: each needs either a filter that must run before fps (and Intel's deinterlacer changes the time base there), a software-only filter, or a decoder the chip lacks; the processor handles the small or rare ones well, and burning subtitles at output size costs little after the picture is small.
- Tell failures apart by their words, never by exit code: 'Failed to find d3d11va adapter by vendor id' = no Intel graphics right now (hide the Intel path, ask again next start); 'Error creating a MFX session' or 'Error initializing a(n) MFX session' = graphics there but Intel's media runtime unusable (say 'update the Intel graphics driver'; ask again next start); '... is unsupported' / 'Error initializing the encoder' / 'Error querying encoder params' = these settings refused (mark this path failed for this ffmpeg version and driver); 'Failed setup for format d3d11' = this kind of film is not decoded by the chip (decode in software for that kind); 'device failed', 'device lost', 'GPU Hang', 'Failed to execute', 'Failed to end frame' = passing trouble (one new run, then the design's existing rule: other path, encoder marked failed). WHY: these are the strings in the pinned source; exit numbers differ between systems (171 and 187 were seen here on Linux for two of them).

### Pitfalls

- -forced_idr 1 is not optional: without it a forced frame is an IDR only when the source frame happened to be a key frame; otherwise it is a plain I frame, which ffmpeg does not mark as a key packet, so the cutter would not see a chunk start.
- This build's h264_qsv defaults to three B-frames and a 250-frame GOP (Jellyfin patch). An unset -bf is not zero.
- Leaving -adaptive_i and -adaptive_b unset leaves the choice to Intel's runtime, which switches them on together with -extbrc 1 or a look-ahead depth, and then puts I frames or IDRs at scene changes. Give both as 0 and never add -extbrc, -look_ahead, -look_ahead_depth, -idr_interval above 0 or the intra-refresh options.
- The design's Intel row has a fixed -b:v 6M: on rungs with a ceiling under 6M Intel raises the ceiling to the target without a word. Target must not exceed -maxrate.
- -global_quality with -maxrate and no -b:v does not give capped constant quality: ffmpeg falls back to fixed quantiser 26 and ignores the ceiling (only a warning). -global_quality alone (ICQ) has no ceiling at all.
- Jellyfin does not force key frames on QSV ('Unable to force key frames using these encoders, set key frames by GOP'), so its experience says nothing about forced IDR landing exactly; and counting frames cannot hit this app's lattice at 23.976/29.97/59.94.
- Any Intel filter (vpp_qsv, scale_qsv, deinterlace_qsv, overlay_qsv) changes the time base to 1/frame-rate of its input and rounds times through 90 kHz. Before fps that can shift frames against the software path; fps and trim must come first and stand next to each other (a jump run pushes thousands of repeats of the first frame through fps for trim to drop; nothing costly may sit between them).
- -hwaccel qsv is not the hardware version of the ordinary decoder: it swaps in Intel's own decoders (different handling after a jump, times re-rounded, no Dolby Vision data). Use -hwaccel d3d11va with hwmap.
- A chain that stays on the card cannot end in format=nv12 (the design's wording 'chain ending format=nv12' fits only chains that end in memory). And -noautorotate is needed with hardware frames or rotated films fail.
- With d3d11va decoding the surface pool is fixed in size; without passthrough=0 on vpp_qsv (or -extra_hw_frames) the run can stop with 'Static surface pool size exceeded.'
- vpp_qsv tonemap=1 on a 10th-generation or older chip returns a picture that was never tone-mapped, with exit 0 and no message. Only the runtime version or a pixel check reveals it.
- Intel drivers 31.0.101.5186/5234 to 5534 (11th generation and newer) show a green or blue picture with normal sound when HDR is tone-mapped on the card; a pixel check in the hardware test (the design already compares the decoded picture) catches it, an exit code does not.
- 'No Intel graphics' is a state, not a fact about the PC: a laptop's graphics-mode switch, a firmware setting, a driver install or a Remote Desktop session can add or remove the adapter. Do not store it as permanent.
- With -loglevel error the line naming the adapter ('Using device 8086:...') and the runtime version are not printed; the probe run needs -loglevel verbose.
- Exit codes are not portable: here the same two failures ended with 171 and 187 (the low byte of FFmpeg's error number on Linux); Windows keeps the whole number. The design's test note that a missing encoder 'exits 255' should not be relied on for 8.1.3 without checking.
- Chunks from h264_qsv and from libx264 (or h264_nvenc) carry different headers; a session must not mix encoders under one init segment. The design's rule (new session spec, page replays) already respects this; a per-chunk fallback would not.
- h264_qsv copies closed-caption data from the source into the stream by default (-a53cc, default true). It does not touch the header, but -a53cc 0 keeps chunk bytes free of it if byte comparisons between runs are ever made.
- Jellyfin clamps h264_qsv to at least 1000 kbit/s ('Bit rate under 1000k is not allowed in h264_qsv'); keep any future low rung above that.
- The Windows build has filters the Linux build cannot show (the d3d11 family); do not conclude from the Linux lists that something is missing or present on the PC.
- Intel's open-source runtime is what I read for the GOP and rate behaviour; the DLL on the owner's PC comes with the graphics driver and may differ in detail, most of all on a 10th-generation chip whose runtime is the old, no longer developed Media SDK.

### Recommended

- WINDOWS HOLDER (code outline, cgo off). var k32 = windows.NewLazySystemDLL("kernel32.dll"); pCreate, pSet, pClear = k32.NewProc("PowerCreateRequest"), k32.NewProc("PowerSetRequest"), k32.NewProc("PowerClearRequest"). type reasonContext struct { Version, Flags uint32; Reason *uint16; _ [2]uintptr } (pads to the full 32-byte C struct on 64-bit). txt, _ := windows.UTF16PtrFromString("Local Media: someone is watching a film"); rc := reasonContext{Version: 0, Flags: 1, Reason: txt}; if pCreate.Find() != nil -> do nothing; h, _, e := pCreate.Call(uintptr(unsafe.Pointer(&rc))); if h == ^uintptr(0) -> failed (e). Hold: pSet.Call(h, 1) then pSet.Call(h, 3); success is r1 != 0. Release: pClear.Call(h, 3); pClear.Call(h, 1); at exit windows.CloseHandle(windows.Handle(h)).  WHY: handle-based, so no thread pinning in Go; type 1 (SystemRequired) stops idle sleep without keeping the screen on; type 3 (ExecutionRequired) is the one the Modern Standby entry sequence waits for; the reason text shows in 'powercfg /requests'. Never set type 0 (display) or 2 (away mode).
- ONE OWNER OF THE HANDLE: a small type guarded by a mutex with Hold()/Release() that are idempotent (PowerSetRequest counts, so two Sets need two Clears; keep the count at 0 or 1). Create the request once at start, close it at exit; if the process dies Windows drops it with the handle.  WHY: a leaked count keeps the laptop awake for ever, which is the complaint Plex gets most.
- WHEN TO HOLD: hold while (a) any stream response is still being written, or (b) an HLS chunk, a direct-play read or a player progress report arrived within the last N minutes; release only after N minutes of none (start with N = 5; Emby used 15 minutes of session activity checked every 5, the Jellyfin plugin 1 minute after the last playback check-in). An open library page that is not playing must not count. Decide deliberately how long a PAUSED film keeps the PC awake and say so in the page.  WHY: Windows 11 may sleep the instant the last request is dropped, players go quiet while they have buffer, and today's lastStream is stamped only at the start of a direct-play response.
- RE-TAKE AFTER A GAP: run a ticker (every 10 s) that compares wall-clock time, time.Now().Round(0), with the previous reading; a jump of more than about 60 s means the PC slept or the program was frozen. Log 'asleep from X to Y, request was held: yes/no, on mains: yes/no' and, if someone is still watching, Clear then Set again (or make a fresh handle).  WHY: Microsoft says requests are 'terminated' on battery and on user-initiated sleep and does not say they come back; the log line is also the evidence that settles the unknowns below through the support bundle.
- TEST AT GITHUB (Windows job, run the test binary directly, not through Git Bash): hold with a unique reason, e.g. "Local Media test " + random hex; out, err := exec.Command("powercfg", "/requests").Output(); if err != nil -> t.Skip("powercfg /requests needs an administrator"); require the reason under both the "SYSTEM:" and "EXECUTION:" headings; release; run again and require it gone. ### Pitfalls

- On battery a Modern Standby laptop sleeps anyway: Windows ends system and execution requests 5 minutes after its sleep timer. With Windows 11's defaults (3 minutes on battery) that is about 8 minutes into an untouched film. Documented, and reported by the Jellyfin plugin's users.
- Closing the lid, pressing the power button, or choosing Sleep ends every request (documented for both APIs). With the default lid action the film stops within seconds to a minute; server and ffmpeg are frozen, not ended, and wake up mid-task with dead connections.
- SetThreadExecutionState from ordinary goroutines is wrong in Go: set on one OS thread, cleared on another, or lost when the runtime retires the thread. If it is ever used as a fallback it needs one goroutine with runtime.LockOSThread that lives as long as the program.
- LazyProc.Call panics when the procedure is missing; call Find() first. Its returned error is never nil, so judge by the first return value only (INVALID_HANDLE_VALUE for create, zero for set/clear).
- Windows 11 can sleep the moment the request is released if the idle time already ran out (the 2-minute afterglow of Windows 10 is gone). Releasing between two chunk requests, between episodes, or the second a viewer pauses will put the PC to sleep under them.
- The repository's present 'watching' signal is too thin for this job: lastStream is stamped at the START of a direct-play response and not by progress reports. A browser reading one long response would be judged idle while still watching. The same signal guards automatic updates (IdleFor() > 15 minutes), so it deserves a look there too.
- The opposite failure is what Plex users complain about for years: a server that never lets the PC sleep (open web-app tabs, DLNA, a leaked request). Only streams and playback reports may count, the hold needs a hard end, and PowerSetRequest's count must never exceed one.
- A request that Windows 'terminated' (battery limit, lid, Sleep) may stay dead after wake although the program still thinks it holds it. Re-take it after every detected gap.
- 'powercfg /requests' cannot be the app's own self-check on the owner's PC: it needs an administrator and the app runs as the ordinary user. It is a test-machine tool. Its text is localised and in the console code page; under Git Bash the argument '/requests' is rewritten into a path.
- PowerRequestExecutionRequired is documented for 'the calling process'. ffmpeg is a child. If Windows ever freezes the child while sparing the parent, chunks stop arriving although the server is awake. Not expected while the PC is fully awake, but unproven during screen-off on Modern Standby.
- PowerToys' documentation says requests from a signed-in user's program stop working once the PC is locked. Microsoft's API reference does not say this. A household laptop is often locked; do not assume either way until the owner's test.
- Lid action 'Do nothing' has a known hazard: a closed, running laptop in a bag overheats. Change it for 'Plugged in' only and say the warning in the checklist. Whether Windows re-checks a lid that is already shut when the plug is pulled I could not confirm.
- A maker's or administrator's policy ('Allow system required requests' = ignore) silently defeats the whole feature; the calls still succeed.
- Linux: before systemd 257 a block lock is ignored for suspend requests made by the same user or by root, so a desktop that suspends through the user's own session may not be stopped; a service account without a login session needs a polkit rule to take a sleep lock; 'sleep infinity' outlives a killed systemd-inhibit unless the whole process group is killed.
- Labels in Windows Settings differ by build (24H2 moved lid controls into Settings and renamed 'Screen and sleep'); I took them from guides, not from a PC. Write checklist steps with a fallback to the Control Panel path, which exists on every build.
- The Modern Standby pages on learn.microsoft.com could not be opened from here. Where this answer cites a 2017 copy or a search summary, re-read the live page once learn.microsoft.com is allowed in the session's network settings, especially 'Display, sleep, and hibernate idle timers' and 'Prepare software for modern standby'.

### What only the owner's PC can settle, and the probe that would

- Is the owner's laptop Modern Standby or classic S3 sleep? PROBE: the app runs 'powercfg /a' and puts output and exit code in the support bundle. 'Standby (S0 Low Power Idle) Network Connected' or '... Network Disconnected' means Modern Standby; 'Standby (S3)' means classic. Cross-check with SYSTEM_POWER_CAPABILITIES.AoAc from powrprof GetPwrCapabilities. (Also settles whether 'powercfg /a' works without an administrator.)
- Does a System+Execution request really keep THIS laptop awake on mains with the screen off? PROBE (owner, plugged in, lid open, do not touch the PC): start a film on the iPhone, let it play 25 minutes. Pass = it plays through. The bundle must show: hold started, mains = yes, no 'asleep from X to Y' gap line. If a gap appears while 'request was held: yes, on mains: yes', Windows ignored the request and the fallback owner text (sleep 'Never' when plugged in) is needed.
- Same on battery: does it stop after roughly sleep timer + 5 minutes as documented? PROBE: same test unplugged for 15 minutes; expect a gap line starting about 8 minutes in on default settings. Confirms the battery warning text and the numbers in it.
- Does a locked PC still honour the request (PowerToys' docs say no, Microsoft's reference is silent)? PROBE: plugged in, film playing on the iPhone, press Windows+L on the laptop, wait 20 minutes. Pass = film continues and no gap line.
- With the lid action left at Sleep, does closing the lid on MAINS stop the film at once (current API text) or does the execution request keep things running (2017 phase table)? PROBE: plugged in, film playing on the iPhone, close the lid for 3 minutes, open it. The gap line gives the exact answer; expect a gap.
- With the lid action set to 'Do nothing' when plugged in, does a film play through with the lid shut, and how warm does this laptop get while the graphics card converts? PROBE: after the owner makes that change, 30 minutes of a film that needs converting with the lid closed; bundle shows no gap, and the conversion speed lines of that session show whether the laptop slowed itself down.
