# M4 "Plays anything": final design

A working document for whoever builds M4 (not written for the owner; the plain-words version is in `PLAN.md` and, once built, `docs/checklists/M4.md`). It came out of three independent designs, three judges and a synthesis, on 2026-11-12. Where the code and this document disagree later, `docs/decisions.md` says which changed and why.

Basis: robust-first (two judges of three) plus the judges' grafts. **Checked** = re-run by me on ffmpeg 6.1 through the real `slice()` in a private clone (the harness was a throwaway test beside `internal/hls`). Nothing has run on the shipped 8.1.3-2; slice 1 is that gate.

## 1. Decisions

1. **One software path carries everything**: H.264 8-bit SDR, cut by M3's cutter on a grid decided beforehand. A graphics card only swaps the encoder, is off until the owner's test passes, and is switched off by its first failure.
2. **Even lattice, 3 s step** (raised so no film exceeds 4,000 chunks), not the key-frame grid: list times are exact (M3's 2 ms check is reused) and nothing is searched before first play.
3. **Jump recipe = `-noaccurate_seek` + `fps=…:start_time` + `trim`** (robust-first plus owner-first's `start_time`). Checked on six films (23.976 with reordered frames; MPEG-2 TS starting at 1.44 s; uneven timing; a 9 s still; sound 10 s longer than picture; H.264 TS with key frames 6 s apart), 17 chunks each, played through and jumped to, copied and converted sound (transport streams: converted only): 0 differences in start times, frame counts, headers or pictures. The other recipes fail: an exact seek shows the next picture inside a still; `trim` before `fps` starts seconds late; robust-first alone mis-times transport streams.
4. **`start_time` is the same in every run** (the picture's first frame). Checked: a per-run anchor half a frame off the raster moved every frame by one.
5. **Lead-in**: 2 s for Matroska and MP4 (the seek lands on a key frame); otherwise `max(2 s, largest key-frame gap + 0.5 s)`, capped at 15 s. Checked: 6 s gaps with a 2 s lead gave right times but the wrong picture (16 dB against played-through); an 8 s lead gave the right one.
6. **The lattice ends at the picture's last frame, and the muxer never stops waiting for the picture** (`-max_interleave_delta 0`). Checked: without the flag, sound that outlasts the picture by over 10 s began 1 s late in the last chunk (robust-first's disclosed fault); with it, 0 problems.
7. **A converted chunk closes when its own data ends** (one fragment is one chunk); readers: 6.5 s down to 3.5 s at 1x. "A jump costs 2.5 s" held only on a fast PC: expect (2 s lead + 3 s chunk + 0.7 s encoder delay) / speed, about 4 s at the 1.5x bar.
8. **Sound is copied beside a converted picture** when the device plays it (AC-3, E-AC-3, AAC from Matroska or MP4), so surround survives. **AAC from any other container is converted, in M3's copy path too.** Checked: M3's command exits 255 on a TS with AAC; with `-bsf:a aac_adtstoasc` it runs, but the header's bit-rate fields differ between runs.
9. **Subtitle mode is its own field**: `track`, `draw`, `burn`. Burn-in is built first and meets the acceptance tests alone; drawing on the PC is a late slice behind a spike.
10. **iPhone rule**: everything is decided before the first chunk. On a device without page fullscreen, picture subtitles are burned in from the first chunk; styled ones are burned in ("as designed", the plan's default) or shown as cleaned plain text, by a per-user preference. The stream is never swapped when the phone enters its own player, picture-in-picture or AirPlay.
11. **Picture burn-in reads the extracted track, not a second open of the film** (which stalls). Checked: with one input a caption already showing at the jump is missing (16.7 dB); with the extracted `.sup` as input 1 it shows (45 dB). Two corrections to that graft: read from its start, a jump 9,000 s in took 71 s (2,990 earlier captions), so the track is sought 120 s back (1.4 s); and `-ss` there counts from the track's first caption (`-seek_timestamp 1` did not help), so that time is recorded at extraction and subtracted.
12. **A Go flattener makes the plain-text version of styled tracks.** Checked: ffmpeg's ASS-to-WebVTT prints drawing commands as captions (`m 0 0 l 800 0 …`), as M3 does today.
13. **Speed is a fact about the PC (one table); decode, network and drawing trouble are lessons about a device.** No trial start (it holds the first picture back and measures logos).
14. **Deferred**: graphics-card decoding and filters (after the owner's test result); swapping streams on surface change; text subtitles inside the chunk list for AirPlay.

## 2. Planner (`internal/playback`, still pure)

`Decide(m Media, c *Caps, w Want, l Limits) Plan`

- `Track` gains Width, Height, FrameRate, Transfer, DoVi (all in `streams`; widen `loadTracks` and `decide`). `Subtitle` gains Kind (text, styled, picture).
- `Caps` gains `Tall` (codec plays above 1080p, from `mediaCapabilities.decodingInfo` supported and smooth), `h264-10`, `dovi5`, `PageFullscreen`, `Draw{Styled,Picture}`.
- `Want{Audio, Subtitle, Styled designed|plain, Lower}`. `Limits{Convert, ToneMap, Encoder, Speed[class][rung], Busy, MaxHeight, MaxRate}` (lessons arrive as limits and trimmed caps, applied in `playCaps`).
- `Plan` gains method `convert`, `Video{Height, Rung, Encoder, HDRToSDR}`, `Subtitles` (none, track, draw, burn), `Lost []string` (4K shown as 1080p, HDR as normal colour, surround as stereo). `handlePlay` marshals the struct; one test pins its JSON keys against `web/src/api.ts`.
- Convert when: the device lacks the codec; the codec cannot be repackaged; the source is taller than the device plays; Dolby Vision profile 5 without `dovi5` (needs `tonemapx`; without it `none`, said plainly); a subtitle is burned; a lesson says so. Still `none`: no picture, no HLS, no AAC.
- Subtitles: text → track. Styled → draw if `Draw.Styled && PageFullscreen`; else burn when Styled is designed, else track (flattened). Picture → draw if `Draw.Picture && PageFullscreen`, else burn. A per-device "draw in the page" switch, offered once that device's renderer has proved itself, waives PageFullscreen (the iPhone's way out when burning is too slow).
- Rungs, in picture-quality order (bufsize is twice the ceiling; a source smaller than the rung keeps its size):

| Rung | Size | Preset | Ceiling |
|---|---|---|---|
| 1 | 1080p | veryfast | 10M |
| 2 | 1080p | superfast | 12M |
| 3 | 720p | veryfast | 5M |
| 4 | 720p | superfast, rates above 30 halved | 5M |
| 5 | 480p | ultrafast | 2.5M |

- An encoder that passed the owner's test replaces libx264 at the same sizes, with its own measured speeds.
- Pick the first rung at or below `Lower`, `MaxHeight` and `MaxRate` whose measured speed divided by (Busy+1) is at least 1.5 (1.2 for 4K HDR). Unmeasured: rung 1 for sources up to 1080p SDR, rung 3 for 4K or HDR. None: `Playable: No`, "This PC cannot convert this film fast enough to watch", quoting the figure, plus "Open in another player".
- `StepDown(plan, evidence, pace, steps) Step` is pure: decode trouble → device lesson for that kind (codec, bit depth, size class); starved with pace under 0.95 over three chunks → PC table lowered, next rung; starved otherwise → network lesson (`MaxRate` 4M, 24 h); renderer failed → `Draw` off. One-way, at most two per play.
- Tests: the 1,890 combinations grow by size, HDR, subtitle kind and surface. Rules: never convert when direct or repackage would play; no rung measured below its bar; burn implies convert; draw only with Draw and PageFullscreen; `Lower` never raises quality; every non-direct plan has reasons.

## 3. Converter (`internal/hls`)

`Spec` gains `Dir string` and `Convert *Convert`, all integers and enums: `Num, Den, AnchorMs, ContainerStartMs, LeadMs`, `Targets []int64`, `W, H`, `Tone` (none, pq, hlg, dovi5), `Deint`, `Encoder` (x264, nvenc, qsv, amf), `Preset`, `MaxRateK`, `Burn{Kind, Track, TrackStartMs, Direct}`.

**PictureFacts** (`facts.go`): one cached ffprobe (new table `picture_facts`): picture start, container start, last frame (read from the final 8 s), rate, field order, pixel shape, colour matrix, largest key-frame gap in the first 60 s (non-Matroska, non-MP4 only). Rates are snapped to 24000/1001, 24, 25, 30000/1001, 30, 50, 60000/1001, 60.

**Lattice** (`lattice.go`): `tick0 = round(start × rate)`; frames sit on whole ticks. `T[k] = ceil(start) + k·step` (whole seconds); `Cuts[k]` = first tick at or after `T[k]`, in ms; `Cuts[0] = tick0`. No cut within 500 ms of the last frame or the end; `EndMs` stays the file's end, so trailing sound sits in the last chunk. Rounding copies the fps filter's (half away from zero); the anchor is nudged 1 ms when within 1 ms of half-way between ticks.

**Command, chunk N > 0.** A = anchor, P = `Cuts[N]` − max(0.1 s, 3 frames).
```
-hide_banner -nostdin -loglevel error
-ss <Cuts[N] − lead − containerStart> -noaccurate_seek -readrate 8 -readrate_initial_burst 60 -i ABSOLUTE_FILE
-map 0:v:0 -vf "[bwdif=mode=send_frame:parity=auto:deint=interlaced,]fps=NUM/DEN:start_time=<A>,trim=start=<P>,PICTURE[,subtitles=f=s<K>.ass:fontsdir=fonts],format=yuv420p"
-c:v libx264 -preset <PRESET> -crf 22 -maxrate <M> -bufsize <2×M> -profile:v high -bf 0 -sc_threshold 0 -g <frames in two chunks + 2> -forced-idr 1
-fps_mode vfr -force_key_frames T[N],T[N+1],…,T[last]
-map 0:a:<a> ( -c:a copy | -af atrim=start=<P> -c:a aac -ac 2 -b:a 192k )
-max_interleave_delta 0   + M3's tail unchanged (-copyts, +1 s, fragmented MP4 to the pipe)
```
Chunk 0: no `-ss`, no `trim`, no `atrim`, list from `T[1]`.

- PICTURE, SDR: `scale=W:H:flags=bicubic,setsar=1`, W and H computed in Go (even, never enlarged, square pixels; the readers' 15-size table is the test).
- HDR, shrink first. Pinned build: `scale…,tonemapx=tonemap=bt2390:desat=0:peak=100:t=bt709:m=bt709:p=bt709:format=yuv420p`. ffmpeg 6.1: `setparams=color_primaries=bt2020:color_trc=smpte2084:colorspace=bt2020nc:range=tv,zscale=w=W:h=H:t=linear:npl=100,format=gbrpf32le,tonemap=tonemap=hable:desat=0,zscale=p=bt709:t=bt709:m=bt709:r=tv` (HLG: `arib-std-b67`). Both add `-color_primaries bt709 -color_trc bt709 -colorspace bt709`. The chain is chosen from `ffmpeg -filters`, read once at start (`Abilities`).
- Picture burn-in: second input `-ss <Cuts[N] − 120 s − trackStart> -i p<K>.sup` (`.mks` for VobSub; no `-ss` when not positive) and `-filter_complex "[0:v:0]…PICTURE[v];[1:s:0]scale=W:H:force_original_aspect_ratio=decrease[s];[v][s]overlay=(W-w)/2:(H-h)/2:eof_action=pass,format=yuv420p[o]" -map "[o]"`. Until the track is extracted, `Burn.Direct` overlays `[0:s:K]` from the film: instant, but a caption already showing at a jump waits for the next. The header is the same either way.
- ffmpeg runs with `cmd.Dir = Spec.Dir` (the server-named subtitle folder); no library path enters filter text.
- Hardware rows, chain ending `format=nv12`: `h264_nvenc -preset p4 -rc vbr -cq 24 -maxrate M -bufsize 2M -bf 0 -g G -forced-idr 1`; `h264_qsv -preset veryfast -b:v 6M -maxrate M -bf 0 -g G -forced_idr 1`; `h264_amf -usage transcoding -quality speed -rc vbr_peak -b:v 6M -maxrate M -bf 0 -g G -forced_idr 1`.
- Length: 4,000 entries of up to six characters, about 24,000 (not 20,300: recordings start at large times). Unit test: under 30,000 with a 259-character path. Reserve on 8.1.3: `-/force_key_frames FILE`.

**Cutter and manager.**
- `fragmentStart` = tfdt + first sample's composition offset − the header's edit-list start (M3's fault on unevenly timed films with reordered frames).
- Converted sessions: each kept fragment must start on `Cuts[cur+1]` within 2 ms, otherwise the run ends as "left the lattice" (and a hardware encoder is marked failed). The chunk is finished when its mdat is copied.
- Per-session step: `reach` 2 chunks, Ahead 120 s, Behind 60 s.
- Relaunch: a second launch only when the failed run used a hardware encoder and served nothing; the session's spec becomes x264 and `OnEncoderFailed` records it. A hardware death later answers `ErrEncoderDied` (HTTP 410); the page replays and the next plan is software. A broken file still starts once.
- `Pace(token)`: film seconds per wall second per chunk, hold time excluded. At most `max(1, cores/4)` picture conversions; beyond that `Open` refuses and the page says the PC is busy converting for another screen.

## 4. Server

**Schema 6** (new migration, new sample database): `devices(id, label, created_at, last_seen_at)`; `sessions.device_id`; `lessons(id, device_id, kind, value, file_id, hits, learned_at, expires_at)`; `picture_facts(file_id, stamp, facts)`; `prefs.styled`. A device is an HttpOnly cookie `lm_device` (400 days, survives sign-out, grants nothing). A lesson holds a kind of file, never a title: the first failure counts for that file, a second file for the kind; 30 days, doubling to 120; network lessons 24 hours; expiry means one quiet retry.

**`settings`**: speed table and hardware results, keyed by ffmpeg version and core count. A benchmark fills it (test button; once after install or update while nobody plays): lavfi-made clips through every rung with the real arguments. Real plays only lower it, only as the sole conversion, and those values expire after 30 days.

| Route | Policy |
|---|---|
| POST `/api/items/{id}/play`: body gains `subtitle, styled, lower, from` | Session |
| POST `/api/hls/{token}/trouble` (evidence in; `wait` or `replay` out) | Session |
| GET `/api/hls/{token}/state` (alive, pace, advice) | Session |
| GET `/api/files/{fileID}/subtitles/{key}/raw`, `/api/files/{fileID}/fonts/{n}` | Session |
| GET `/api/device`, DELETE `/api/device/lessons/{id}` | Session |
| GET `/api/devices` | Owner |
| POST `/api/hardware/test`, GET `/api/hardware`, PUT `/api/settings/hardware` | Owner |
| POST `/api/items/{id}/open-local` (loopback and same origin; path from the database through `openMedia`) | Session |
| GET `/api/items/{id}/handoff.xspf`, `/handoff` (link signed at the click) | Session |

**Subtitles** (`internal/subs`): one ffmpeg pass per file writes every subtitle track (`s<N>.ass`, `p<N>.sup`, `p<N>.mks`) and every font by position (`-dump_attachment:t:K f<K>`) into `cache/subs/<file>-<stamp>/` and records each track's first timestamp. While a styled track is read, play answers `wait` with a percentage and offers "Start now with plain words". Sidecars gain `.sup` and `.idx`.

**Hardware probe**: ten seconds of testsrc2 at 1080p through the real arguments, 15 s limit. Pass = exit 0; key frames on three lattice points and nowhere else; byte-identical headers from two runs; the decoded picture matches the source (SSIM); faster than x264 rung 1. The button answers in plain words ("This PC converts ordinary films at full HD and 4K HDR films at 720p. Your graphics card can / cannot help.").

**Header** gains `script-src 'self' 'wasm-unsafe-eval'` only in slice 8, with explicit types for `.wasm` and `.woff2`.

## 5. Web player

- `caps.ts`: `decodingInfo` at 1080p and 2160p, `h264-10`, `dvh1.05`, `document.fullscreenEnabled`; drawing proven lazily (8-byte module, `transferControlToOffscreen`, renderer ready within 4 s, else a lesson).
- Video element carries `data-method`, `data-rung`, `data-subtitles`. M3's pins stay.
- Watchdog for starts and stalls: words after 3 s, a card after 12 s (lighter picture; Open in another player on a PC; Back).
- `stall.ts`: 8 s starved, 3 stalls in 60 s, or one of 12 s; hls.js `bufferStalledError` and `fragLoadTimeOut` (`maxTimeToFirstByteMs` 30000); fatal decode errors; over 20% dropped frames twice. Never within 10 s of a start, seek, track switch or tab shown, nor while paused. It posts `trouble`; on `replay` it plays again at the same position with a notice and Undo. It asks `state` 12 s into a converted play (stepping down early if the server advises it) and on unlock (replaying quietly if the session has gone).
- The "Why is this converting?" panel lists `Lost` and has "Colours look wrong on this device" (records a lesson: convert HDR for it). Settings: "Test hardware acceleration"; "Learned about this device" with Forget; all devices for the owner.
- "Open in another player": on the server PC `open-local`; elsewhere a VLC file (`.xspf` with `start-time`) and a selectable link, saying the link opens that one film without sign-in for 12 hours.
- Slice 8: JASSUB 2.5.37 and libbitsub 1.13.2 by dynamic import (`worker: {format: 'es'}`), the app's own fullscreen button on the wrapper, a `fullscreenchange` handler that moves fullscreen from the video to the wrapper, `disablePictureInPicture` while a subtitle is drawn, licence notices shipped.

## 6. Acceptance tests

1. **1.5x / 1.2x**: `TestSoftwareKeepsUp` (`LM_SPEED=1`) in the Linux job at GitHub on the pinned build: a generated 1080p film, and a generated 4K HDR film (HEVC Main10 PQ, fixed 25 Mbit/s), each at the rung the planner picks from that machine's own benchmark. Best of three; fails loudly on fewer than four cores.
2. **Never a too-slow setting**: property test over random speed tables.
3. **Failing graphics card**: a session forced to `h264_nvenc` (exits 255 on every runner) is served by x264, `starts == 2`, encoder marked failed. A fake converter (the test binary re-executed) dies after two chunks: 410, next plan software. A stub proves the probe rejects an encoder with no key frame at the forced time. The broken-file test keeps `starts == 1`.
4. **Pixels in Chromium**: ASS rectangles drawn with `\p1` (no font), a PGS file from a Go generator, VobSub made from it; the e2e screenshots the burned video at a time with a caption, one without, and after a jump into a caption; tolerance 40 per channel. After slice 8 the same for drawn subtitles.
5. **iPhone fullscreen**: planner rows (no page fullscreen × styled-designed or picture → convert and burn); hls test (burned frames equal played through and jumped to); from slice 8 a synthetic `webkitbeginfullscreen` must leave `data-subtitles="burn"`.
6. **Stall**: the e2e delays chunks: `data-rung` changes, the lesson is listed, the next play starts lower, Forget restores.

## 7. Slices, in order

0. **M3 cutter fixes.** `fragmentStart`; AAC copied only from Matroska and MP4. Tests: uneven-timing reordered fixture and a TS with AAC and 6 s key-frame gaps in `TestEveryChunkBeginsWhereTheListSays`.
1. **Converter, not reachable.** Lattice, PictureFacts, Abilities, command builder, early close, lattice check, Pace. Tests: the six-film twin of the M3 test with a picture comparison (first frame and one second in, at least 25 dB; wrong pictures measured 10 to 17, right ones 29 and up), including a cut at 21 s of 23.976 film (a rounding comparison gets it wrong); lattice-versus-ffmpeg first frame over starts 0 to 100 ms; command length; typed arguments. `[all-os]` on the pinned build, plus a throwaway speed job for the 4K HDR clip, because its result fixes the rung table.
2. **Planner and play.** `convert`, Limits, rungs, Lost, JSON pin, handlePlay, page. Tests: planner table and rules; e2e plays an MPEG-4 (ASP) MKV, which every browser must have converted.
3. **Sizes, HDR, deinterlacing, Dolby Vision rule.** Tests: 15 sizes; PQ ramp and HLG (monotonic, mid-grey in range, BT.709 tags) on both chains.
4. **Speed table, benchmark, conversion cap, "too slow".** Tests: acceptance 1 and 2.
5. **Subtitles burned in.** Extraction, flattener, generator, both burn paths, iPhone rule. Tests: acceptance 4 and 5; a jump 9,000 s into a track with 3,000 captions under 3 s; a track whose first caption is late.
6. **Devices, lessons, stall step-down, watchdog.** Tests: acceptance 6, `StepDown` table, migration sample, keyboard reach of Undo and Forget.
7. **Hardware test and fallback.** Tests: acceptance 3; the rest is the owner's button.
8. **Drawn subtitles on the PC.** Spike first: both renderers draw in headless Chromium over plain HTTP under the widened header, with no console error. Fails: stop, burn-in stays.
9. **Open in another player.** Tests: loopback only, fresh signature, keyboard reach.
10. Decisions, checklist (iPhone surfaces, VLC download, stall counters in the support bundle), status line.

## 8. Measured speeds (2026-11-12)

`packaging/speed-probe.sh` on GitHub's four-processor Linux machine with the pinned converter (jellyfin-ffmpeg 8.1.3), 20-second films made with moving noise so that they cost about as much to decode as real ones; best of two runs; film seconds per second:

| Source | Setting | Speed |
|---|---|---|
| 1080p H.264, 8 Mbit/s | decoding only | 17.0x |
| | 1080p veryfast (rung 1) | 3.8x |
| | 1080p superfast (rung 2) | 5.2x |
| | 720p veryfast (rung 3) | 5.9x |
| | 720p superfast (rung 4) | 7.3x |
| | 480p ultrafast (rung 5) | 10.2x |
| 4K HEVC 10-bit PQ, 25 Mbit/s | decoding only | 3.7x |
| | tonemapx, 1080p veryfast / superfast / ultrafast | 1.67x / 1.84x / 2.06x |
| | tonemapx, 720p veryfast / superfast / ultrafast | 2.22x / 2.26x / 2.44x |
| | tonemapx, 480p veryfast / superfast / ultrafast | 2.66x / 2.67x / 2.76x |
| | zscale + tonemap, 1080p / 720p superfast | 1.66x / 2.26x |

What follows from it: the five rungs stand. An ordinary film converts at well over twice the 1.5x bar at every rung on four processors. A 4K HDR film at 25 Mbit/s clears its 1.2x bar at 1080p (1.67x) with little to spare, and decoding is what it costs: the 4K picture decodes at only 3.7x before anything else is done, so a 60 Mbit/s disc copy will be slower and may need 720p, and a second viewer at the same time will not fit. The two tone-mapping chains are equally fast, so the choice between them is about what a build has, not speed. These runs had no `fps` filter, forced key frames or sound; the real command will be a little slower.

## 9. Known gaps

4K HDR at 1.2x may hold only at 720p, or not at all for high-bit-rate copies; `tonemapx`, hardware encoders, the iPhone and Dolby Vision profile 5 cannot be tested here. Until slice 8 passes its spike, styled and picture subtitles cost a full conversion on every device. `fps` forces a constant rate: slight judder on films with truly mixed timing.
